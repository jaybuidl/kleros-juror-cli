# `history` — a CLI path to a dispute's period timeline

Status: ready-for-agent
Category: enhancement
Reported by: @blaisebuidl (autonomous juror agent consuming the CLI)
Source: `../report-blaisebuidl.md`, item 2

> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement

**Summary:** A new `history` command emitting a dispute's period timeline, reconstructed from
`NewPeriod` and `DisputeCreation` logs.

**Current behavior:**
`status` answers "what now" and cannot answer "what happened". On a finished dispute it reports
`period: execution`, `deadline: null`, `actionRequired: none` — correct, and useless for a
post-mortem. Reconstructing a timeline today means a bespoke script: `NewPeriod` logs plus a
`getBlock` per log, roughly four RPC round trips per dispute. A stored `status` blob cannot tell you
whether a window was genuinely short or merely observed late.

**Desired behavior:**

A `history` command taking `--dispute` and the RPC-selection option, and nothing else. It needs no
signing key, no vote IDs, no juror address and **no dispute kit** — period transitions are a
KlerosCore concept, so it skips dispute-kit resolution entirely and is cheaper than `status`.

It emits a flat, chronological `timeline` array. Each entry:

```jsonc
{
  "period": "commit",              // evidence | commit | vote | appeal | execution
  "startedAt": "1756661199",       // decimal unix seconds, as a string
  "endedAt": "1756662999",         // null while the period is still open
  "elapsedSeconds": "1800",        // actual, endedAt - startedAt; null while open
  "periodDurationSeconds": "1800", // nominal budget; null in execution
  "endedEarly": false              // null when either operand is null
}
```

Settled during triage, each overriding some part of the reporter's original sketch:

1. **A command of its own, not `status --history`.** `status` is juror-scoped and requires
   `--votes`; a timeline is neither. A flag that swaps a command's payload shape is worse for a
   JSON-parsing consumer than a distinct envelope.
2. **Flat and chronological, with no `round` field.** `NewPeriod` carries no round, so attribution
   would have to be inferred by counting `appeal -> evidence` transitions. Inferring a fact and
   presenting it as read is the exact failure mode that produced this report.
3. **`endedEarly` is strictly arithmetic**: `endedAt < startedAt + periodDurationSeconds`. It makes
   **no causal claim**. The logs record that a period changed, never who closed it or why. The
   reporter's own caveat applies: they have only observed early exits they themselves caused, and
   are reasoning from contract source rather than from a negative observation. A causal reading
   would encode that unverified reasoning into a field an agent then trusts.
4. **`elapsedSeconds` for actual, `periodDurationSeconds` for nominal.** The reporter's
   `durationSeconds`/`budgetSeconds` pair collides head-on with this codebase, where `periodDuration`
   already means the *nominal* budget and issue 01 is publishing it as `periodDurationSeconds`.
   Shipping both would make "duration" mean nominal in `status` and actual in `history`, for the
   same consumer, about the same concept. One word, one job.
5. **The `evidence` period is included.** `NewPeriod` fires on *entry* to a period, so nothing fires
   when `evidence` begins — that moment is dispute creation. A timeline built from `NewPeriod` alone
   would have a start time for every period except the first, and its earliest entry would carry an
   `endedAt` with no matching `startedAt`. `evidence`'s `startedAt` comes from `DisputeCreation`.
6. **The still-open final period is included, with `endedAt`, `elapsedSeconds` and `endedEarly` all
   `null`.** This preserves one rule worth stating in the docs: **every non-null field in a timeline
   entry is final**. Two calls an hour apart return identical values for every field that has one,
   which is what makes the output safe to store and diff. Live countdown stays `status`'s job.

**Key interfaces:**

- **One `getLogs` against KlerosCore**, `fromBlock: 0n` to `"latest"`, filtered server-side on
  `topics[1] = disputeID`, OR'd over `topic0` for both `NewPeriod` and `DisputeCreation`. Both
  events carry the dispute ID as their first indexed parameter, so a single query returns both.
  This is **better bounded than the log query this repo already ships** — `identifyDisputeKit`
  delegates to the contracts package's `getDisputeKitsViem`, which runs the same full range with no
  topic filter at all.
- **One `eth_getBlockByNumber` per distinct block**, deduped by block number. Roughly five per
  dispute, more with appeals. Do **not** read `blockTimestamp` off the log: viem declares the field
  but only passes through whatever the node returned, never requests it, and no standard
  `eth_getLogs` supplies it. A timestamp whose source varies by provider is precisely the kind of
  value this feature exists to make trustworthy.
- **Two `eth_call`s**, batched through the existing multicall helper: the core `disputes(...)`
  getter for the court ID, then `getTimesPerPeriod(courtID)` for the nominal budgets.

**A caveat that must be documented, not silently absorbed:**
`getTimesPerPeriod` returns the court's **current** configuration. If a court's period lengths were
changed after a dispute ran, `periodDurationSeconds` — and therefore `endedEarly` — reflect today's
budget, not the one in force at the time. Recovering the historical value would need a second layer
of log archaeology over court-parameter changes, which is out of scope. Say so plainly in the
command description and the README rather than letting a consumer assume otherwise. This is the same
class of error the whole report is about.

**Failure behavior:**

`history` is the **first read in this tool with no `eth_call` fallback**. Every other read degrades:
`identifyDisputeKit` catches a refused `getLogs` and falls back to `getDisputeKitsLength` /
`disputeKits`, with a test driving a transport that throws `"query returned more than 10000
results"`. No such path exists here — the contract stores only `lastPeriodChange` for the *current*
period, so past transitions live nowhere but in logs.

So when the log query is refused, **fail loudly**: a stable `code` (`HISTORY_UNAVAILABLE`), a
message naming the cause, and a `cta` telling the caller to point `ARBITRUM_RPC` at a log-capable
endpoint. **Never return a partial timeline.** A truncated timeline that looks like a timeline is
the same class of error as the bare `deadline` that started this report. This follows the CLAUDE.md
invariant: fail loudly and fast, never retry quietly.

A dispute that cannot be read should reuse the existing `DISPUTE_NOT_FOUND` code rather than
inventing a second one.

**Acceptance criteria:**

- [ ] `history --dispute N` emits a chronological `timeline` with one entry per period the dispute
      has entered, beginning with `evidence`
- [ ] The command accepts no `--votes`, `--address` or `--dispute-kit`, and runs with no signing key
- [ ] `evidence.startedAt` comes from `DisputeCreation`; a test asserts the first entry is `evidence`
- [ ] `NewPeriod` and `DisputeCreation` are fetched in **one** `getLogs` call, topic-filtered on the
      dispute ID
- [ ] Block timestamps are fetched per **distinct** block, deduped — a dispute with two transitions
      in one block causes one block fetch, not two
- [ ] For every closed entry, `startedAt + elapsedSeconds == endedAt` exactly
- [ ] `endedEarly` is `true` iff `endedAt < startedAt + periodDurationSeconds`, and `null` whenever
      either operand is `null` — asserted directly, with a case for each branch
- [ ] The open final period has `startedAt` set and `endedAt`, `elapsedSeconds`, `endedEarly` all null
- [ ] `execution` has `periodDurationSeconds: null` and `endedEarly: null`
- [ ] Every timestamp and duration is a decimal string or `null` — never a JSON number, never ISO-8601
- [ ] A refused log query returns `HISTORY_UNAVAILABLE` with a `cta`, and **no** `timeline` key —
      covered by a test that drives a transport throwing on `eth_getLogs`, mirroring the existing
      dispute-kit fallback test
- [ ] The command description and `README.md` both state the current-court-configuration caveat
- [ ] `README.md`'s command reference and output section cover the new command and envelope
- [ ] `CONTEXT.md` gains an **Ended early** glossary entry stating that the term is arithmetic and
      makes no claim about cause. Coordinate with issue 03, which edits the neighbouring **Deadline**
      entry
- [ ] `docs/adr/0007-*` records the no-fallback decision: why this read fails hard where every other
      read degrades, and why a partial timeline was rejected. Per `CONTEXT.md`/`CLAUDE.md`
      convention, the ADR lands in the same change as the behavior
- [ ] A fork test covers the timeline against a real dispute, skipping when its prerequisite is
      absent like the other fork suites. Archive RPC: `mesc url arbitrum_alchemy`
- [ ] `pnpm typecheck`, `pnpm lint` and `pnpm test` all pass

**Out of scope:**

- Round attribution, inferred or otherwise
- Recovering historical court configuration
- Any change to `status`, including its envelope — issue 01 owns that
- Adding a `--history` flag to `status`
- Chunking or range-limiting the log query; the topic filter already bounds the result set, and no
  chunking helper exists in the codebase to reuse

**Triage record.** Reached `ready-for-agent` through one grilling session, eight questions over two
rounds, all resolved. Three claims in the original report were corrected along the way:

1. The "second unbounded log path" objection triage itself raised was **wrong and is withdrawn** —
   `NewPeriod._disputeID` is indexed, so this query is better bounded than the existing one.
2. The reporter's `durationSeconds`/`budgetSeconds` naming collides with the codebase's existing
   `periodDuration`.
3. The reporter's shape omits the `evidence` period, which has no `NewPeriod` log.

The genuine architectural cost turned out not to be range bounding but the **absence of any
`eth_call` fallback** — hence the ADR requirement.
