# `status` exposes the period clock, not just the derived deadline

Status: ready-for-agent
Category: enhancement
Reported by: @blaisebuidl (autonomous juror agent consuming the CLI)
Source: `../report-blaisebuidl.md`, item 1

> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement

**Summary:** `status` should emit the two inputs its deadline is computed from, so an agent can
inspect the period clock instead of reconstructing it.

**Current behavior:**
`status` reports `deadline` and `secondsRemaining`. Both are derived from `lastPeriodChange` and
`timesPerPeriod[period]`, and neither input survives into the payload. An agent handed only a
`deadline` has to invent a model of where it came from; the reporting agent invented the wrong one
and concluded a window had been shortened when it had merely been observed late. A stored status
blob currently cannot distinguish those two cases after the fact.

Half the plumbing already exists. `PreflightFacts` carries `periodDuration` — `timesPerPeriod[period]`,
null in `execution` — populated by the pre-flight read and consumed by the deadline warnings, but
never emitted. `lastPeriodChange` is read from the core `disputes(...)` getter, passed to
`deadlineFor()`, and then discarded; it is not a field on `PreflightFacts`.

**Desired behavior:**
`status` additionally emits three keys:

- `periodStartedAt` — `lastPeriodChange`, decimal unix seconds as a string
- `periodDurationSeconds` — `timesPerPeriod[period]`, decimal unix seconds as a string, `null` in
  `execution` where no budget is defined
- `periodClock` — the constant string
  `"deadline = periodStartedAt + periodDurationSeconds; each period's timeout runs from its own start"`,
  emitted unconditionally

Two decisions the maintainer settled during triage, which override the reporter's own example:

1. **Decimal unix seconds as strings, not ISO-8601.** Every numeric in this envelope is already a
   decimal string (`dispute`, `round`, `gas`, wei values), and `deadline` is published that way in
   `kleros-juror-cli@0.1.0`. The reporter's example showed ISO for both the new fields and
   `deadline`; adopting it would either put two timestamp formats in one object or break installed
   consumers. `deadline` and `secondsRemaining` are not touched.
2. **`periodStartedAt` is not null in `execution`.** The reporter's sketch implies it mirrors
   `deadline`'s nullability. It should not: `lastPeriodChange` is a real, known timestamp in every
   period including `execution`, and emitting it there tells a caller when a finished dispute
   reached execution — which is a small down payment on the timeline that issue 02 asks for.
   Only `periodDurationSeconds` is null in `execution`, because `timesPerPeriod` covers
   `evidence..appeal` only.

**Key interfaces:**

- `PreflightFacts`: gains a field carrying `lastPeriodChange`. The value is already read on the
  pre-flight path and thrown away; this stops discarding it.
- `deadlineFor()`: unchanged. It already receives both operands.
- The `status` payload shape: three new keys. No existing key changes type, name or meaning.
- Write-command payloads (`commit`, `reveal`, `vote`): unchanged.

**Acceptance criteria:**

- [ ] `status` on a dispute in `evidence`, `commit`, `vote` or `appeal` emits `periodStartedAt`,
      `periodDurationSeconds` and `periodClock`
- [ ] A test asserts `periodStartedAt + periodDurationSeconds == deadline` exactly, for every period
      where `deadline` is non-null — the invariant is machine-checked, not left to inspection
- [ ] In `execution`: `periodDurationSeconds` is `null`, `deadline` stays `null`, `periodStartedAt`
      is still the real timestamp, `periodClock` is still present
- [ ] All timestamp/duration values are decimal strings or `null` — never JSON numbers, never ISO-8601
- [ ] `deadline` and `secondsRemaining` are unchanged in both format and value
- [ ] The existing unit coverage for deadline arithmetic is extended to the new fields
- [ ] `README.md`'s output/envelope section documents the three new keys — per `CLAUDE.md`, the
      README restates the JSON envelope, so a change to the envelope is a change to it
- [ ] `pnpm typecheck`, `pnpm lint` and `pnpm test` all pass

**Out of scope:**

- Any change to `deadline` or `secondsRemaining`, including their format
- `status --history` and anything reading `NewPeriod` logs — that is issue 02
- Documenting the invariant in `SKILL.md` or `CONTEXT.md` — that is issue 03
- Adding these fields to the write commands' payloads; `status` only for now
